# Adversarial Design Review — H2SEP Room Checklist PWA

## Findings

**1. BLOCKER — The three designs specify three incompatible item schemas. The app cannot be built as written.**
- Design A: `status: "pending"|"complete"|"issue"` (one enum) + `note`, ids `gr600_a`/`gr600_b`.
- Design B: two orthogonal fields — `check` (null|stamp) and `issue` (null|{note,resolved}) — and explicitly renders the state **"checked AND open issue"** ("installed but damaged", state table 4.1) plus "Resolve & check".
- Design C: `status: "open"|"done"|"issue"`, ids `gr600`, `gr600_2`.
A's and C's single-enum models **cannot represent B's "checked with open issue" state**, and B's "Resolve & check" / resolved-issue-history flows are unimplementable on them. The id schemes also collide (`gr600_a` vs `gr600_2`), which breaks A's idempotent-merge argument (§2.5) the moment Claude-ingested rooms and app-created rooms coexist.
**Fix:** canonical item shape = B's semantics in A's container: `items.{id} = { code, label, sort, checked: bool, initials, checkedByName, checkedByUid, checkedAt, checkedAtLocal, issue: string|"" , issueResolved: bool, deleted }`. Keep A's atomic-full-write invariant per tap (write the whole check* group in one `updateDoc`; write the whole issue* group in one `updateDoc`). Standardize ids on A's `gr600_a/_b` everywhere, including C's ingestion JSON (`key` field). Update C §3.1 accordingly before any ingestion happens.

**2. BLOCKER — Design A §2.8 is wrong about iOS: an installed PWA and a Safari tab do NOT share storage.** Since iOS 16.4, a Home Screen web app runs in its **own storage container**, separate from Safari. `persistentMultipleTabManager()` only coordinates tabs *within one container*. Consequences the designs miss:
- A crew member who starts checking rooms **in Safari before installing** builds a mutation queue in the Safari container. Installing to Home Screen starts a **fresh, empty container** — those queued offline check-offs are stranded in Safari and then subject to the 7-day ITP eviction. This is the one realistic path to **silently lost check-offs**, and it happens on day one, during onboarding, exactly when people fiddle before installing.
- Two containers = two anonymous uids and two 190-read initial syncs per person (minor quota inflation, real confusion in `checkedByUid`).
**Fix:** the app must refuse to be used un-installed on iOS: if `navigator.standalone !== true` (and UA is iOS), show the install screen (S8) as a **gate, not a banner** — read-only browsing allowed, checking disabled until installed. Onboarding order becomes: install → name/initials → check. Keep A's other iOS claims (Home Screen exempt from 7-day cap, own container, eviction under storage pressure possible) — those are correct.

**3. RISK — Queued-write loss has no recovery story beyond "sync daily." Add a dirt-cheap backup lane.** A is honest that container eviction/icon deletion kills the queue and offers only procedural mitigation. Accept that — but the design has **no backup at all** against the larger loss surfaces: vandalism (finding 6), B's "Reset room", an admin mishap, or a bad Claude ingest overwriting live data. **Fix:** weekly (or on-demand) export by Claude: a session reads all rooms via REST (~190 reads, noise) and commits `backup-YYYYMMDD.json` to the **private** `SH0T250/Claude` repo. One message from Austin ("back it up") or a Routine. This converts several irreversible failures into 5-minute restores. Should be in v1 ops, not "later."

**4. RISK — Quota math is directionally right but the "3 opens/day" assumption is the soft spot.** Recomputed: a checker walking corridors opens the app dozens of times/day; only reopens after a **>30-min disconnected gap** trigger the full re-read, but on a construction site with dead zones, most reopens *will* qualify (offline time counts as disconnected). Worst realistic case: 10 devices × 8 qualifying reopens × 190 docs = 15,200 reads + fan-out ~3,000 + initial syncs ≈ **~20K/day = 40% of quota**. Still safe at 10 devices — but the stated 5× headroom is really ~2.5×, and 15–20 devices during a punch blitz could hit the ceiling. **Fix:** implement A's lever #1 (floor-scoped listener) in v1, not as a deferred option — it's one `where('floor','==',n)` clause and cuts the dominant term ~4×. Doc-size math checks out (realistic ~9–11 KB/doc counting field-name overhead; 1 MiB limit is a non-issue). One-doc-per-room is the right call; the 1-write/sec/doc soft limit is irrelevant at tap rates.

**5. RISK — B's UI copy promises an audit trail that A explicitly cut.** B references it three times: un-check "written to the audit trail (`uncheckedBy`)", issue-note replacement "previous note kept in the audit trail", conflict section "audit trail keeps both events." A §1.8 skips the activity log in v1 — so none of that exists. Un-checking someone else's mark **destroys the record that it was ever checked**. **Fix (pick one):** (a) strip all audit-trail copy from B and accept destructive un-check for v1 (defensible — paper had no audit trail either); or (b) ship A's reserved day-doc activity log, appends only on `uncheck` and `issue-replace` (the two destructive events), ~10 writes/day. (b) is small; I'd take it, but (a) is acceptable. Do not ship UI text claiming logging that doesn't happen.

**6. RISK — Security honesty is good, but state the blast radius plainly and take the two free mitigations.** With anonymous auth, anyone who finds the public URL can mint a token and, passing `validRoom`, **overwrite every room's `items` map** (rules validate shape, not preservation). For furniture checklists this is acceptable at $0 — agreed — but the designs never say "total data wipe is possible." **Fix:** (a) the backup lane in finding 3 is the real mitigation; (b) don't link the app URL from the public repo README and use a non-obvious repo name — obscurity is worthless against targeting but effective against crawlers; (c) note the upgrade path (App Check, email allowlist) in the README and move on. Also: do **not** enable Firebase's optional auto-delete of anonymous accounts (it would orphan `checkedByUid` mappings) — add this to C's setup steps as a "leave it off" note.

**7. RISK — C's setup step 5 has Austin paste permissive placeholder rules; A's real rules never get deployed.** As written, the go-live path publishes `allow read, write: if request.auth != null` on everything and nothing schedules replacing it — the admin PIN enforcement, shape validation, and delete-prevention in A §4.3 silently never exist. **Fix:** C step 5 pastes A's full rules text (with the PIN hash pre-substituted by Claude in chat). One source of truth. Also: A's rules use `hashing.sha256(...).toHexString()` — the `hashing` namespace exists in the rules language, but **verify the exact string-input/`.lower()` chain in the Rules Playground before go-live**; if it fights back, fall back to storing `pinHash` comparison client-side + a simpler rules check, and accept UI-gate-only admin for v1.

**8. RISK — Concurrent un-check/check UX will mislead, and B's own conflict note contradicts the model.** B 4.5 says the same-box-offline race is benign ("both wrote a check; both agree it's done") — but the un-check-vs-check race is the misleading one: a checker sees their initials for hours offline, then sync flips the box empty (someone un-checked) or to someone else's initials, **with no notification** (the coalesced toast only fires for live changes while on-screen). The room can silently drop below 100% after a super already reported it done. **Fix:** cheap and sufficient — on listener-driven transitions of an item from checked→unchecked or initials-change, always show the flash + a toast even post-sync (the snapshot diff makes this detectable); and the Home hero recomputes live, so counts self-correct. Accept LWW; just don't suppress the signal. Keep A's dual-timestamp display ("checked 9:14 AM · synced 3:40 PM") — it's the honest answer to stamp-integrity questions.

**9. NIT — A §2.5's "two phones create room 205 with different types" leaves a Franken-room** (union of two templates' items, one type label). Rare, admin-fixable, correctly disclosed. Add one guard: the app's Add Room flow warns when the number already exists in cache — that kills the common case (both phones online-ish) for free.

**10. NIT — Whole-row tap = check, no confirm, is right for speed but wrong next to the flag icon.** A 44px flag target flush at the row end of a 56px row invites mis-taps that instantly stamp initials (undo requires tap → sheet → un-check). **Fix:** give the flag a 8–12px dead zone, and make the *first* accidental-feeling check (check within 400ms of a scroll gesture ending) show the 5s Undo toast that B already specs for un-check.

**11. NIT — Manifest inconsistency between B and C.** B: `start_url: "./index.html#/"`, `scope: "./"`; C: absolute `/h2sep-checklist/`. Both work if the manifest sits at repo root, but pick one (C's absolute form is less fragile under iOS's occasionally-weird base-URL handling in standalone mode). Also `apple-mobile-web-app-capable` is deprecated in favor of `mobile-web-app-capable` — ship both meta tags.

**12. NIT — Vendored Firebase ESM bundles are ~300–500 KB.** Fine functionally, but precache them in the SW with the versioned cache name and make sure the update banner's "tap to refresh" calls `skipWaiting` + reload — a stale SW serving an old app against new rules/schema is the classic Pages-PWA failure. C already specs the banner; wire it, don't just design it.

**13. SCOPE — Design B is roughly 2× a v1.** Everything below is deferrable without touching the hard requirements, and cutting it is the difference between "Austin uses it this week" and a three-week build:
- **Cut:** S5 template management UI (templates are seeded by Claude via REST; in-app "duplicate room" can copy an existing room doc), S6 drag-reorder editor (keep only inline "+ Add item"), bulk range-add, group-by-category toggle, S9 print view, the **two-theme system** (ship ONE theme — Triun navy; the free/pro theme split is manufactured scarcity that doubles CSS surface), "Issues pseudo-floor", long-press context menus on room cards, admin auto-lock timer, "only admin can un-check" settings toggle, member roster (§1.7), `Reset room` (dangerous with no audit log — defer behind finding 3's backups).
- **Keep despite temptation to cut:** offline pill + pending dots, quick-pick issue chips (they encode Austin's exact paper vocabulary), prev/next footer, go-to-room keypad, the install gate.

**14. SCOPE/OPS — C's corrections stand up; adopt them verbatim.** New public repo (private-repo Pages is correctly identified as blocked on Free; confidential contents correctly bar making `Claude` public), deploy-from-branch over Actions, `.nojekyll`, one manual Settings→Pages click, Blaze-only Storage (photos are correctly Pro-tier), skip both app stores (the 12-tester/14-day Play rule alone kills it for this crew size). No findings against C's §1–2 beyond findings 7 and 11.

## v1 Ship List

**Data (Firestore, Spark):**
- Unified item schema per finding 1 (orthogonal `checked` + `issue`, A's `_a/_b` ids, atomic per-group writes, soft deletes, `merge:true` creates).
- `rooms/{number}` one-doc-per-room, `config/app`, templates seeded by Claude via REST (no template UI).
- A's security rules (finding 7), PIN admin enforcement if `hashing` verifies, else UI-gate PIN only.
- Floor-scoped listeners from day one (finding 4).

**App screens:** S1 Home (hero + floor cards), S2 Floor grid + filter chips + floor switcher, S3 Room checklist (full spec: sticky header, ★ notes, item rows, issue sheet with quick-picks, prev/next footer), S4 Add/Edit room (single room, template dropdown — no bulk range), S7 Settings (name/initials, admin PIN, sync status), S8 Onboarding with **iOS install gate** (finding 2), go-to-room keypad. One theme: Triun navy.

**PWA/deploy:** new public repo `SH0T250/h2sep-checklist`, app at root, `.nojekyll`, deploy-from-branch `main`, versioned SW precache (app shell + vendored Firebase) + update banner, manifest per finding 11, QR code for the trailer.

**Ops:** C's 8-step Firebase setup with A's rules pasted in step 5 and "leave anonymous auto-delete off"; Claude REST ingestion loop with C's non-destructive merge rule and A's id scheme; **weekly JSON backup to the private repo** (finding 3).

**Explicitly deferred:** activity log (unless option 5b chosen), template/item editors, print/PDF, photos (Blaze), custom domain, app stores, member roster, reset room, second theme.

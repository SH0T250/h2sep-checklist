# Phase 0 — What the H2SEP 3D Room Viewer Actually Is
Research agent report · 2026-08-14 · repo: /home/user/h2sep-checklist

## 1. Executive answer for Austin

**There are no imported BIM/3D model files anywhere in this project.** Your 3D room viewer is a
**single self-contained HTML page** in which every wall, bed, sink and grab bar is **hand-authored
JavaScript code** — procedural Three.js geometry (scaled unit boxes/cylinders) written by prior
Claude sessions on 2026-08-09, working from the **architect's dimension strings on sheet A555**
("Enl. Guest Room Plans & Elevs — QQ Std., QQ Ext., & QQ Std. Conn."), the floor plans A100–A103,
the bathroom sheet A530, and your Room 101 field sheet. The "format" of your model is therefore:
**JavaScript source code embedded in an HTML file, rendered live by an inline copy of Three.js r128.**
Nothing was exported from Revit, SketchUp, Blender, or any BIM tool, and there is no .gltf/.glb/
.obj/.fbx/.ifc/.rvt/.dwg file in the repo (verified by full-tree search — zero hits).

## 3. Format & library — exact findings

`preview101/room101-3d.html` contains **four inline `<script>` blocks** (no external `src=`, no CDN):
1. Line 301: runtime-error overlay (paints errors into `#err`).
2. Line 311: **Three.js r128, official minified bundle** — header `@license Copyright 2010-2021
   Three.js Authors, SPDX MIT`, and `const e="128"` (the minified `REVISION` constant). ~590 KB —
   the bulk of the file size.
3. Line 320: **OrbitControls + MapControls**, non-minified r128-era examples code, wrapped in an
   IIFE that attaches `THREE.OrbitControls` (classic global-script style, not ES modules).
4. Line 1368: the authored exhibit app (~1,140 lines, `'use strict'` IIFE), header comment:
   `/* H2SEP - Room 101 - QQ Studio Connector - FF&E exhibit app */`.

**Loader check (decisive):** `GLTFLoader` 0 hits; `OBJ/FBX/IFC/Collada/STL/DRACO/FileLoader` and
`ObjectLoader` appear only INSIDE the minified three.js core bundle (the single one-line bundle at
line ~311/317) — never called by the authored code. One `base64` hit, also bundle-internal. No
scene-JSON payloads, no data URIs of geometry, no `<canvas>`-external assets. **Geometry is 100%
procedural.**

## 4. How the geometry is authored

- Unit primitives shared by all meshes: `var BOX = new THREE.BoxGeometry(1,1,1)`, `CYL =
  CylinderGeometry(1,1,1,20)`, `SPH = SphereGeometry(1,16,12)` (preview lines 1507–1509).
- `box(x1,y1,z1, x2,y2,z2, mat)` places a scaled unit cube between two corner points;
  `cyl(cx,cz,r,y1,y2,mat)` likewise. **96 `box(` calls, 17 `cyl(` calls** in the preview.
- Units are **feet**; x runs across the room width, z from the corridor wall (0) negative toward
  the window wall, y up. Room 101 source envelope: `W = 13.17, D = 36.4, H = 9.0, T = 0.35`
  (wall thickness), `BATHX = 6.55, BATHZ = -11.5`.
- Room shell: translucent walls (`MeshStandardMaterial opacity 0.25, DoubleSide, depthWrite:false`)
  with solid base bands + top edge lines (`wallSeg()`), window with glass/mullions, entry door
  ajar, ceiling outline via `LineSegments`, ghost slabs for Room 103 and the corridor as context.
- Every scoped item is registered via `reg({id,tag,grp,name,qty,cat,desc,note,flag,focus,dist})`
  into `PARTS` — **42 `reg({` calls** — and its meshes attached via `attach()` which tags
  `mesh.userData.pid` and pushes to `pickables` for raycasting. Descriptions cite the drawings
  verbatim (A555 line numbers, A530 legend, G402 blocking/reach-band notes, A600 remark a,
  P104 vs cutsheet divergences, the field sheet's "GR-308R ×2" discrepancy).

### 4.1 ROOM_GEOM — per-room parameterization (added by the builder, v1.12–1.16)
Injected before geometry executes; keyed by room number from `?room=` query param:
`{w, d, conn, mirror, variant, basis}` with constants `QQ_W = 12.0`, `WIDE_W = 12.948`
(12'-11 3/8" clear), `QQ_D = 36.417` (36'-5" clear), `EXT_D = 38.75` (38'-9" clear) — all off A555.
- **47 entries** (counted in both builder and built file; matches `MODEL_ROOMS` in `js/config.js`
  lines 35–42, which gates the 3D button in the app): 8 QQ Studio Connector (101 103 · 215 236 ·
  336 · 401 403 · 436), 31 QQ Studio, 2 QQ Wide (201 301), 6 QQ Extended (230 232 330 332 430 432).
- `mirror` reflects the plan about the room centreline (even side of the double-loaded corridor);
  `basis` records HOW handedness was decided, with honest flags: "CONFIRM ON PLAN" /
  "HANDEDNESS UNCONFIRMED" surface in the on-screen caveat strip.
- `conn:false` rebuilds a solid demising wall and skips the entire GR-3 door assembly, its tag,
  cyan wash light, legend row and sidebar row. `PARTNER_OF` maps connecting pairs off A100–A103;
  room 215's partner is deliberately blank (not named on A101).
- **A room not in ROOM_GEOM gets a hard "NO 3D MODEL FOR ROOM x YET" full-page stop** rather than
  another room's geometry — this is Austin's standing ruling 7 (SESSION_HANDOFF.md lines 248–279).

### 4.2 Materials, lighting, camera, labels
- **Materials:** one `MAT` palette of ~30 `MeshStandardMaterial`s (preview 1442–1485): wood/woodDk,
  linen, upholstery, chrome, porcelain, counter, appliance, emissive TV screen, emissive lampshades,
  glass, Triun-cyan door materials (`cyanDr`/`cyanFr`, brand #02A9E0 with emissive), red flag
  material, ghost context. Highlight = emissive swap (cyan 0.01/0.55/0.75, red for flagged).
- **Lighting:** HemisphereLight + shadow-casting DirectionalLight (2048px map, tuned bias) +
  cyan PointLight washing the connecting door + 5 warm interior PointLights. Ground plane +
  double GridHelper (dark/light theme pair). Fog. `PCFSoftShadowMap` desktop / `PCF` mobile.
- **Camera:** PerspectiveCamera FOV 35 (→42 portrait), OrbitControls with damping, polar clamp
  0.495π, distance 4–260. Five presets in `VIEWS` (iso/top/beds/bath/kitch) + `ISO_PORTRAIT`,
  cubic-eased tween, per-part `focus`/`dist` fly-to on select. `?view=`, `?freeze=1` (render
  on demand via `requestRenderIfFrozen`), `prefers-reduced-motion` honored.
- **Labels:** HTML `div.lbl` chips absolutely positioned each frame + SVG leader lines/dots in a
  fixed `#leaders` svg (`addLabel`/`tagLbl`, preview 2003–2031). ~47 labels with priority tiers
  (pri 4 major → pri 1 chips, culled first), screen-space collision/fan-out via signed dx, and
  the builder's zoom-reveal pass. Tags default OFF on phones; TAGS chip restores.
- **UI:** sidebar/bottom-drawer part list grouped by category (`ORDER`, 41 ids + GR-3), qty/ADA/
  FLAG chips, tap-to-select → info card (`showCard`) with tag, qty, category, description, note.
  Light/dark theme. Legend. Caveat strip: "LOCATIONS STYLIZED — NOT SHOP DRAWINGS" + per-room
  variant/dimensions/mirroring confidence.

## 6. Assessment for the BIM Hub rebuild

### What's reusable
- **The dimension data and semantics are gold:** ROOM_GEOM (w/d/mirror/conn/variant/basis),
  PARTNER_OF, the 42-part PARTS registry with A555/A530/G402-cited descriptions, tag anchors, and
  the honest-uncertainty pattern (basis strings, caveat strip, hard-stop for unmodeled rooms).
  All of it is plain JS data that can be lifted into any new pipeline.
- The interaction model (tap-object → info card, part registry keyed by tag, emissive highlight,
  priority-tiered labels, view presets, on-demand render) is exactly the UX a BIM hub needs and
  is worth porting as a pattern even if no code is reused.
- The builder's anchor-patch approach proved reproducibility but is fragile by design — it should
  NOT survive into the rebuild; parameterization belongs in source, not in patches.

### Hard limits of the current viewer
1. **Per-room only** — one room per page load; no floor or whole-building assembly (geometry is
   authored in a single room's local coordinates; corridor/neighbor are non-interactive ghosts).
2. **QQ family only** — 47 of 115 keys. King family (58+ keys), One Bedroom, QQ Acc have NO model.
3. **No layer system** — no FF&E/MEP/plumbing/electrical/doors/finishes toggles; MEP is not
   modeled at all (scope was FF&E + appliances + bath accessories; PTAC is context-only).
4. **No object→submittal links** — the info card shows text; refs live separately in
   `refs.html`/`refs/refs-101.json`, joined by item code, not from the 3D scene.
5. **Three.js r128 (May 2021)** — pre-WebGPU, pre-`three/examples/jsm`-only era, global-script
   build that three.js no longer ships; ~5 years and ~50 releases behind current.
6. **Geometry is code, not assets** — nothing exports cleanly to Blender/GLTF today; boxes only,
   no named object hierarchy beyond `userData.pid`.
7. Stylized placements — item locations are explicitly "STYLIZED · EXHIBIT ONLY," not takeoff-grade.

### Recommendation: keep Three.js, upgrade the approach
Keep **Three.js (current release, ES modules, GLTFLoader + DRACO/meshopt)** as the runtime.
Rationale vs alternatives:
- **Babylon.js**: capable but a full rewrite for no capability Austin needs; heavier runtime;
  the team's existing knowledge (and test harness hooks) are Three-shaped.
- **IFC.js / That Open Company**: right answer only if authoritative IFC exists. There is no IFC —
  the architect's set is PDFs; generating IFC from A555 dimension strings would be fabricating a
  BIM. Revisit if the design team ever supplies a Revit/IFC export.
- **Staying on r128 inline**: fine for the shipped crew exhibit (do not churn it), wrong base for
  the hub — no GLTF/KTX2/WebGPU path, no module ecosystem.

### Concrete recommended pipeline (BIM Hub)
1. **Author in Blender** (metric-off, feet), one .blend per room type + a shared FF&E asset
   library; every object named `TAG__instance` (e.g. `GR-300__bed1`) and assigned a **collection
   per layer** (FFE / PLUMBING / ELECTRICAL / HVAC / DOORS / FINISHES / SHELL). Seed the Blender
   scenes from the existing ROOM_GEOM numbers + PARTS registry (scriptable via bpy — the current
   box() calls translate almost 1:1).
2. **Export glTF (.glb)** per room type (KHR_materials, Draco or meshopt compressed). Custom
   properties → glTF `extras` carry `{tag, qty, cat, layer, submittalId}` so the viewer needs no
   side table for basics.
3. **Viewer:** current three (ES modules), GLTFLoader; instantiate room-type GLBs per ROOM_GEOM
   (position/mirror via matrix — mirroring now safe if assets are exported with symmetric
   normals, or bake both hands in Blender to avoid winding issues entirely); layer toggles =
   toggling collections/groups by `extras.layer`; raycast → `extras.tag` → info card + deep link
   to the submittal/refs record (join on tag, the same key refs-101.json already uses).
4. **Whole-building merge:** rooms become instances placed on a floor-plate scene from A100–A103
   grid coordinates; corridor/common areas modeled once. LOD/visibility per floor.
5. **Keep the honesty features:** basis/confidence metadata per room, hard-stop or explicit
   "UNMODELED" state for rooms without geometry, stylized-placement caveat until dimensions are
   field-verified.
6. Migration order: lift ROOM_GEOM + PARTS into JSON (they are already data), build the King
   Studio in Blender first (it has no model and A550 extracts exist in Drive), then re-export QQ.
